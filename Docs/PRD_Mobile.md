# 코토다망 최장 단어 탐색기 — 모바일(Flutter) 버전

데스크톱(WPF) 앱을 스마트폰에서 쓸 수 있게 만든다. WPF는 모바일에서 실행 자체가 불가능하므로 UI뿐 아니라 핵심 로직(단어 탐색 엔진, 캐릭터 데이터 모델, 스크린샷 덱 인식)까지 Flutter/Dart로 새로 구현하는 **완전 별도 앱**이다. 데스크톱과 데이터는 공유하지 않는다.

| 항목 | 내용 |
|---|---|
| 대상 | 신규 프로젝트 (데스크톱 KotodamanWordFinder v1.26.0과는 별도 코드베이스) |
| 플랫폼 | Android 우선 (1차), iOS는 범위 밖 |
| 배포 방식 | APK 사이드로드, 기존 다운로드 사이트(`download-site/`, Vercel)에 모바일 섹션 추가 |
| 기술 스택 | Flutter/Dart, `opencv_dart` (온디바이스 ORB 매칭) |
| 데이터 공유 | 없음 — 모바일은 자체 로컬 저장소만 사용 |
| 신규 백엔드 | 0개 (서버 불필요, 완전 오프라인 동작) |

---

## 1. 왜 이 구성인가

데스크톱 앱은 `net8.0-windows` + WPF + `OpenCvSharp4.Windows`로 만들어져 있다 (`KotodamanWordFinder.csproj`). 이 세 가지 전부 Windows 전용이라 모바일에서 그대로 실행하는 선택지는 없다. 남는 선택은 셋뿐이다.

| 선택지 | UI 통제력 | 로직 재사용 | 비고 |
|---|---|---|---|
| 모바일 웹/PWA | 브라우저 엔진에 위임 | 핵심 로직만 JS/TS로 이식 | 스토어 불필요, 가장 적은 작업량이지만 오프라인·카메라 접근이 제약적 |
| **Flutter (채택)** | 자체 렌더링(Skia) — 기종 상관없이 동일하게 보임 | Dart로 전량 재작성 | `opencv_dart`로 온디바이스 이미지 인식 가능 |
| React Native | 네이티브 컴포넌트 위임 — 기종별 편차 | JS/TS로 전량 재작성 | OpenCV는 네이티브 모듈을 직접 작성해야 함 |
| 완전 별도 네이티브 (직접 Kotlin/Swift) | 최상 | 전량 재작성 | 작업량 최대, 이번 범위에선 과함 |

**결정: Flutter.** "화면이 가시적으로 명확하게 보이도록" 만들어야 한다는 요구사항은 OS·기종에 따라 렌더링이 달라지는 RN보다 자체 렌더링 엔진을 쓰는 Flutter와 궁합이 좋다. 스크린샷 덱 인식(ORB 매칭)도 `opencv_dart` 바인딩으로 온디바이스 처리가 가능해 서버 없이 데스크톱과 동등한 기능을 유지할 수 있다.

## 2. 포팅 대상 (데스크톱 → 모바일)

데스크톱의 `Models/`, `Services/` 중 이번 범위에 필요한 것만 추린다. 전부 C#/WPF 종속 코드라 로직을 그대로 가져올 수 없고, Dart로 새로 짜야 한다 — 이 표가 이식 작업량의 실체다.

| 데스크톱 원본 | 역할 | 모바일 이식 필요 여부 |
|---|---|---|
| `Services/WordSearchService.cs` (614줄) | 단어 사전 인덱싱 + 최장 단어 탐색 | **필수** — §3 FR-1 |
| `Models/CharacterEntry.cs` (328줄) | 캐릭터 데이터 모델. 속성/종족/문자 외에 모드시프트·문자상태·리더효과·덱그룹효과까지 포함 | **필수, 단 1차는 `Letters`+`DeckRestrictionGroupId`만** — §4 D-6 |
| `Models/DeckPreset.cs` | 덱 프리셋 (이름 + 캐릭터ID 목록) | 필수, 구조 단순 |
| `Services/DeckScreenshotRecognitionService.cs` (1,454줄) | ORB 매칭 + 속성색 보조 판정으로 스샷에서 캐릭터 인식 | **필수** — §3 FR-4, 최대 리스크 지점 |
| `Services/DeckScreenshotLearningService.cs` | 검수 결과를 속성색 학습 샘플로 축적 | 선택 — 없어도 기본 HSV 판정으로 동작(§3 FR-4) |
| `Services/CharacterWebImportService.cs`, `CharacterLibraryService.cs`의 관리자 기능 | GameWith/코토다망DB 자동 크롤링, 캐릭터 일괄 편집 | **제외** — §7 |
| `Services/DataUpdateService.cs` (델타 업데이트 3-way merge) | 공식 데이터 업데이트 병합 | **제외** — 모바일은 앱 재설치로 데이터 갱신(§3 FR-6) |

## 3. 기능 요구사항

### FR-1 — 단어 탐색 엔진 `P0`

덱에 편성된 캐릭터들이 제공하는 문자(가나)로 만들 수 있는 최장 단어를 사전에서 찾는다.

- 사전 규모: `gaccag_words.json.gz` 기준 21만+ 항목, 2.6MB(gzip). 앱에 내장 asset으로 번들.
- 데스크톱 로직 그대로 이식: 단어 길이 2~7자만 대상. **4~7자는 직접 탐색**, **2~3자는 콤보 사전**(다른 단어와 조합해 더 긴 결과를 만드는 보조 탐색)으로 분리 처리.
- 입력: 현재 손패(최대 4명 캐릭터)가 제공하는 가용 문자 집합. 출력: 만들 수 있는 최장 단어(동률 시 후보 목록).
- 첫 실행 시 사전 인덱싱에 걸리는 시간이 체감되지 않아야 한다 (목표: 저사양 기기에서도 1초 이내 — 검증 필요, §6).

### FR-2 — 캐릭터 데이터 `P0`

캐릭터 2,319명(`characters.json`, 2.1MB) + 이미지 자산(`CharacterImages`, 71MB)을 모바일에 내장한다.

포팅할 필드: `Attribute`(火水木光闇天冥虹), `SubAttributes`, `Species`, `GroupName`, `Letters`(기본 제공 문자), `AlternateForms`(동일명 모드시프트), `LetterStates`(조건별 문자 상태), `OneTimeLetters`(1회용 문자), `DeckRestrictionGroupId`(동시 편성 제한), `MiracleLeaderEffect`/`DeckGroupLetterEffect`(리더·그룹 조건부 문자 부여).

**1차 범위: `MiracleLeaderEffect`·`DeckGroupLetterEffect`·`LetterStates`는 1차 제외 · 2차 필수 구현(확정, §4 D-6).** `characters.json`(2,319명) 실측 결과 이 세 효과 중 하나라도 가진 캐릭터는 **80명(3.4%)** 뿐이다 — `MiracleLeaderEffect` 2명(0.1%), `DeckGroupLetterEffect` 43명(1.9%), `LetterStates` 36명(1.6%). `AlternateForms`(동일명 모드시프트)도 3명(0.1%)으로 소수라 1차 제외. 나머지 96.6%는 `Letters`(기본 문자) + `DeckRestrictionGroupId`(동시 편성 제한)만으로 정상 동작한다.

- 1차에서 이 80명은 기본 문자만 반영된 채로 노출된다(효과 미적용, 캐릭터 자체를 숨기지 않음) — 데스크톱과 결과가 달라질 수 있는 캐릭터라는 뜻.
- **캐릭터 상세/덱 편집 화면에 "고급 효과 미지원(2차 예정)" 배지를 표시한다.** 사용자가 왜 이 캐릭터만 결과가 다른지 오인하지 않도록 하는 최소 조치 — 조용히 누락시키지 않는다.

### FR-3 — 덱 편집 `P0`

덱(최대 12명, `DeckEditorWindow.xaml.cs`의 `MaximumDeckSize`)과 손패(그중 탐색에 쓸 4명, `MainWindow.xaml.cs`의 `HandSize`)는 별개 단계다 — FR-1의 "손패 4명"은 이 12명 중에서 고른 결과다.

- 덱 편성: 최대 12명, `DeckRestrictionGroupId`가 같은 캐릭터는 동시 편성 불가.
- 손패 선택: 편성된 덱 12명 중 탐색에 쓸 4명을 선택 (데스크톱과 동일하게 4명 고정).
- 덱 프리셋 저장/불러오기 (이름 + 캐릭터ID 목록, `DeckPreset.cs` 구조 그대로).
- 캐릭터 검색은 이름 + `SearchAliases`(한글 별칭) 기준.

### FR-4 — 스크린샷으로 덱 인식 `P0`

게임 화면 스크린샷 한 장에서 덱 카드 배치(4×3 슬롯)를 자동 인식해 캐릭터를 채운다.

- **온디바이스 처리** (결정 완료, §4 D-3). 서버 전송 없음, 오프라인 동작.
- 데스크톱과 동일한 2단계 판정: ① ORB 특징점 매칭으로 상위 후보 산출 ② 문자 원 테두리 색으로 속성 보조 판정(색 판정은 실패해도 ORB 결과를 덮어쓰지 않고 동점 후보 정리에만 사용 — 데스크톱 v1.23.7 로직 그대로).
- 학습 참조 이미지(`RecognitionReferences`, 4.6MB) 번들 필요. 사용자별 학습 축적(`DeckScreenshotLearningService`)은 1차 범위에서 제외 가능 — 기본 HSV 판정만으로도 데스크톱 문서 기준 "확신 낮으면 보정 안 함"이라 안전망이 있음.
- 인식 결과는 검수 화면에서 사용자가 확인/수정 후 확정 (자동 확정 아님).

### FR-5 — 화면 가시성 (모바일 전용 신규 요구사항) `P0`

데스크톱 UI를 그대로 축소하지 않는다. 일반 스마트폰 세로모드(폭 360~430dp, 예: iPhone 14/갤럭시 S 시리즈) 기준으로 새로 설계한다.

- 최소 폰트 크기 14sp, 본문 기준 16sp 이상. 가나 문자 슬롯(핵심 정보)은 20sp 이상.
- 터치 타겟 최소 44×44dp (문자 슬롯, 캐릭터 카드, 하단 액션 버튼).
- 캐릭터 카드 그리드는 한 화면에 과밀 배치하지 않는다 — 데스크톱 12칸 덱판을 한 화면에 욱여넣지 말고 스크롤 또는 4명 단위 섹션으로 분리.
- 시스템 다크모드 대응 (라이트/다크 둘 다 텍스트 대비 확보).
- 접근성: 시스템 폰트 크기 확대 설정을 앱이 존중해야 함(고정 px 대신 sp/스케일 단위 사용).

### FR-6 — 데이터 갱신 `P1`

신규 캐릭터 추가나 사전 갱신을 사용자에게 전달하는 경로. 1차 범위는 **매번 APK 전체를 새로 받는 방식**으로 충분 — 데스크톱처럼 데이터만 바뀐 부분을 델타로 병합하는 인프라(3-way merge)는 이식하지 않는다(§7). 사용자가 만든 덱 프리셋은 로컬 저장소에 남아 앱 업데이트로 사라지지 않아야 한다.

- 갱신 흐름: 앱이 `latest.json`의 `mobile.version`을 확인 → 최신이 아니면 배너로 안내 → 탭하면 앱이 백그라운드에서 새 APK 전체를 내려받고 `REQUEST_INSTALL_PACKAGES` 기반 네이티브 설치 다이얼로그를 띄운다. 사용자는 설치 화면에서 탭 한 번만 하면 되고, 브라우저로 이동할 필요는 없다(근거는 §4 D-4). 완전 무탭 자동 업데이트는 Android 보안 모델상 불가능 — 데스크톱 Velopack과의 차이점.

## 4. 결정 사항

### D-1 — 기술 스택 → **Flutter**

React Native 대비 자체 렌더링으로 기종 편차가 적고, `opencv_dart` 바인딩으로 온디바이스 인식(FR-4)을 서버 없이 구현할 수 있다는 점이 결정적이었다. §1 비교표 참고.

### D-2 — 1차 배포 플랫폼 → **Android만**

데스크톱 배포가 이미 다운로드 사이트 + 직접 배포 방식(`Docs/PRD.md` 참고)이라 모바일도 같은 관례를 따른다. iOS는 App Store 심사·개발자 계정 비용이 추가로 들어가 1차 범위에서 제외.

### D-3 — 스크린샷 인식 처리 위치 → **온디바이스**

서버로 이미지를 보내는 방식은 백엔드 구축·이미지 업로드 비용·온라인 필수라는 부담이 생긴다. 데스크톱도 로컬(OpenCvSharp) 처리라 아키텍처 일관성도 맞는다. 저사양 기기에서 ORB 매칭 속도는 실기기 검증이 필요(§6 리스크).

### D-4 — 배포 채널 → **APK 사이드로드, 기존 다운로드 사이트에 통합**

Play 스토어 심사(개인정보처리방침, 콘텐츠 등급 등)를 1차에서 건너뛰고 데스크톱과 동일하게 다운로드 링크로 배포한다. 새 사이트를 만들지 않고, 이미 배포된 `download-site/index.html`(Vercel) 하단에 **모바일 다운로드 섹션을 추가**한다.

- 지금 사이트는 GitHub raw `latest.json`(리포 `sksmsaidkeu/Kotodaman_Simulator`)을 fetch해 Windows 버튼 하나를 채우는 정적 페이지 하나뿐이다(`download-site/index.html:105`). 서버 로직 없음 — 이 구조를 그대로 재사용한다.
- APK도 데스크톱 Setup.exe와 같은 패턴으로 GitHub Releases 자산으로 올린다. `latest.json`에 `apkUrl`·`apkSha256`·모바일 버전 필드를 추가해, 사이트가 fetch 한 번으로 두 플랫폼 버튼을 모두 채우게 한다(별도 매니페스트 파일 불필요 — 데스크톱과 모바일은 버전 주기가 다르므로 필드는 `mobile` 하위 객체로 분리, 예: `mobile.version`/`mobile.apkUrl`/`mobile.apkSha256`).
- 릴리스 태그는 데스크톱(`vX.Y.Z`)과 충돌하지 않게 `mobile-vX.Y.Z` 접두사를 쓴다.
- Android는 출처를 알 수 없는 앱 설치이므로 사이트에 "설치 허용" 안내 문구가 필요하다(데스크톱의 SmartScreen 우회 안내와 같은 자리, `Docs/PRD.md` §4 D-2 참고).
- **완전 무탭 자동 업데이트(Velopack 상당)는 불가능, 원탭 인앱 업데이트는 가능.** Android 8+ 보안 모델상 `REQUEST_INSTALL_PACKAGES`로 설치하는 일반 앱은 자기 자신을 갱신할 때도 시스템 설치 확인 다이얼로그를 반드시 거친다(특권/기기관리자 설치자가 아닌 이상 우회 불가) — 이 점은 데스크톱과 근본적으로 다르다. 다만 "브라우저로 이동해 수동 다운로드"보다 훨씬 나은 중간 지점이 있다: 앱이 백그라운드에서 APK를 내려받고 `FileProvider` URI로 설치 인텐트를 띄워, 사용자는 네이티브 설치 다이얼로그에서 **탭 한 번**만 하면 된다(F-Droid·Obtainium 등 사이드로드 배포 앱의 표준 패턴). 1차 목표는 이 원탭 흐름으로 잡는다 — §3 FR-6에 반영.
  - (참고) Android 12+에는 특정 조건(같은 설치자·같은 서명)에서 이 확인 다이얼로그 자체를 생략하는 API가 있다고 알려져 있으나, 조건이 까다롭고 제조사별 편차 가능성이 있어 1차 목표로 확정하지 않는다. 구현 단계에서 여력이 되면 검증 후 적용.

스토어 심사 대응은 사용자 규모가 커지면 재검토.

### D-5 — 데이터 공유 → **공유 안 함**

모바일은 자체 로컬 저장소만 쓴다. 사용자별 덱/캐릭터 수정 데이터를 데스크톱과 동기화하려면 클라우드 백엔드가 필요한데, 이번 범위에서는 그 비용이 기능 대비 과하다고 판단.

### D-6 — 캐릭터 고급 효과(리더/그룹/문자상태) → **1차 제외, 2차 필수 구현(확정)**

`characters.json` 2,319명 실측: `MiracleLeaderEffect` 2명(0.1%), `DeckGroupLetterEffect` 43명(1.9%), `LetterStates` 36명(1.6%) — 셋 중 하나라도 해당하는 캐릭터는 80명(3.4%)뿐이다. `AlternateForms`도 3명(0.1%)으로 소수.

**결정**: 1차는 `Letters`(기본 문자) + `DeckRestrictionGroupId`(동시 편성 제한)만 지원한다. 96.6%의 캐릭터는 이걸로 데스크톱과 동일하게 동작하고, 나머지 3.4%(80명)는 1차에서 기본 문자만 반영된 채로 노출된다(효과 미적용, 캐릭터 자체는 숨기지 않음).

**주의 — 이건 "안 해도 되는 기능"이 아니라 "순서를 미룬 기능"이다.** 데스크톱에 이미 구현·배포된 기능이라, 미포팅 상태로는 해당 80명 캐릭터를 편성했을 때 데스크톱과 결과가 달라진다(실제 게임 최적 편성과 어긋날 수 있음). 비율이 낮다는 이유로 2차 계획에서 조용히 빠지지 않도록 아래를 못박는다.

- 2차 착수 시점 필수 작업으로 취급한다 — "여유 되면" 항목이 아니다.
- 80명 명단은 `MiracleLeaderEffect.IsEnabled`/`DeckGroupLetterEffect.IsEnabled`/`LetterStates` 비어있지 않음 조건으로 `characters.json`을 필터링하면 언제든 재추출 가능(이번 검증에 쓴 것과 같은 방식).
- 2차 범위: ①덱 내 리더/그룹 조건을 평가하는 계산 로직 ②캐릭터별 문자상태 선택 UI ③이 결과를 `WordSearchService` 가용 문자 계산에 연결(§3 FR-1 참고, 데스크톱 `CharacterEntry.GetAvailableLetters()`와 동등한 배선).
- 1차 배포 화면(캐릭터 상세/덱 편집)에 "고급 효과 미지원" 표시를 넣어 사용자가 결과 차이를 오인하지 않게 한다 — §3에 FR-2 하위 항목으로 반영.

## 6. 리스크 / 오픈 이슈

1. **온디바이스 ORB 매칭 성능.** 데스크톱은 OpenCvSharp(네이티브 x64)라 여유 있지만, 저사양 안드로이드 기기에서 `opencv_dart`가 같은 속도를 낼지는 검증 전. 느리면 인식 대상 슬롯을 줄이거나(4×3 전체 대신 부분) 해상도를 낮춰 대응.
2. ~~캐릭터 데이터 변환 스크립트 필요.~~ **해소(2026-08-31): 변환 불필요.** `characters.json` 2,319명 전수 검사 결과 순수 UTF-8 텍스트(비ASCII는 `\uXXXX` 이스케이프)이고, C# 전용 타입 판별자(`$type` 등) 없이 표준 JSON 배열이며, 모든 레코드에서 필드별 타입이 일관됨(문자열/불리언/배열/중첩객체 혼용 없음). Dart `dart:convert`의 `jsonDecode`로 그대로 파싱 가능 — 가장 게으른 경로(필드명 그대로 재사용) 그대로 채택.
3. **iOS 확장 시 재검토 필요.** `opencv_dart`의 iOS 지원 여부, 이미지 자산 71MB가 App Store 심사 정책에 걸리는지는 1차 범위 밖이라 미확인.
4. ~~최소 지원 Android 버전 미정~~ **해소(2026-08-31): API 26(Android 8.0)로 확정** (§5). `opencv_dart` 공식 예제의 minSdk가 24, Flutter 자체 최소 지원이 21~24대이므로 이 둘은 걸림돌이 아니고, `REQUEST_INSTALL_PACKAGES` 기반 원탭 업데이트(§4 D-4)가 API 26부터 동일하게 동작하는 게 실질적 하한선.

## 7. 다루지 않는 것

### 7.1 — 1차 범위 밖 (필요 시 재검토)

- iOS 배포 (§4 D-2)
- 데스크톱-모바일 데이터 동기화 (§4 D-5)
- 캐릭터 웹 반자동 등록(GameWith/코토다망DB 크롤링), 캐릭터 일괄 편집기 — 관리자 전용 도구로 데스크톱에 남는다
- 델타 데이터 업데이트·3-way merge 인프라 (§3 FR-6) — 앱 재설치로 대체
- 사용자별 스크린샷 인식 학습 축적(`DeckScreenshotLearningService`) — 기본 HSV 판정으로 1차 대응, 부족하면 2차 검토
- Play 스토어 정식 출시, 개인정보처리방침 작성 (§4 D-4)

### 7.2 — 1차 제외 · 2차 필수(확정, 누락 아님)

- 캐릭터 리더 조건부 문자(`MiracleLeaderEffect`)·그룹 조건부 문자(`DeckGroupLetterEffect`)·문자상태 전환(`LetterStates`)·동일명 모드시프트(`AlternateForms`) — 해당 캐릭터 80명(3.4%). 데스크톱에 이미 있는 기능이라 "구현 안 해도 되는 것"이 아니라 "순서를 미룬 것"이다. 2차 착수 시 최우선 작업으로 취급(§4 D-6).

## 8. 작업 순서

아래 0~4단계는 전부 **1차 범위**(요약표 기준) 안에서의 순서다. §4 D-6(리더/그룹효과/문자상태)은 1차 완료 후 2차로 착수 — 순서에 넣지 않는다(§7.2).

위험도·의존성 순으로 잡았다: 가장 먼저 막힐 수 있는 지점(§6 오픈 이슈)부터 없애고, 화면 없이 검증 가능한 로직 → 첫 실제 화면 → 그 위에 기능을 얹는 순서다.

### 0단계 — 실현 가능성 확인

§6에 남은 오픈 이슈 중 착수 여부 자체를 좌우하는 것만 먼저 없앤다.

- `opencv_dart`로 실기기(저사양 안드로이드)에서 `RecognitionReferences` 샘플 몇 장 ORB 매칭 — 속도가 안 나오면 D-3(온디바이스 처리)부터 재검토(§6-1).
- `characters.json`을 Dart에서 변환 없이 파싱 가능한지 확인(§6-2).
- 최소 지원 Android 버전 결정(§6-4) — Flutter 프로젝트 생성 시 `minSdkVersion`에 바로 들어가므로 스캐폴딩 전에 정한다.

**완료 기준**: 두 스파이크 결과(정성적 판단 — 실사용에 지장 없는 속도인지)와 최소 OS 버전 숫자가 나오면 다음 단계로. 여기서 막히면 D-3·D-1(기술 스택) 자체를 재검토.

### 1단계 — 단어 탐색 엔진 (FR-1, 화면 없음)

`Id`/`Name`/`Letters`만 있으면 되는 범위로 좁힌다 — `Attribute`/`Species`/`SearchAliases`/`DeckRestrictionGroupId`는 화면(2단계)에서나 쓰이는 필드라 여기서는 불필요, 이미지 자산도 아직 필요 없음(첫 화면은 2단계).

- 사전(`gaccag_words.json.gz`) 로딩 + 4~7자 직접탐색/2~3자 콤보사전 로직을 Dart로 이식.
- 고정 테스트 입력(캐릭터 ID 4개 → `Letters` 합집합)으로 최장 단어 결과 산출.

**완료 기준**: 데스크톱 앱에서 같은 캐릭터 4명으로 뽑은 결과와 동일한 결과가 나오는 골든 테스트 1개 이상 통과.

### 2단계 — 덱 편집 + 화면 가시성 기반 (FR-2 나머지 필드, FR-3, FR-5)

처음으로 실제 화면이 나오는 단계. FR-5(최소 폰트/터치타겟/그리드 규칙)를 재사용 가능한 기반으로 먼저 세우고 그 위에 화면을 얹는다 — 이후 3단계 화면도 이 기반을 그대로 쓴다.

- `Attribute`/`Species`/`GroupName`/`SearchAliases`/`ImageFileName` 포함 캐릭터 데이터 전체 필드 + 이미지 자산(71MB) 번들링.
- 덱 편성(최대 12명, `DeckRestrictionGroupId` 제약) 화면 + 손패 선택(덱 12명 중 4명, `HandSize`) 화면.
- 덱 프리셋 저장/불러오기 — 로컬 저장 방식 결정 필요(개수가 적어 단순 key-value/JSON 파일 저장으로 충분, 별도 DB 불필요).
- 캐릭터 검색(이름 + `SearchAliases`).

**완료 기준**: 1단계에서 검증한 탐색 엔진이 이 화면에서 만든 손패로 실제 동작.

### 3단계 — 스크린샷 덱 인식 (FR-4)

가장 리스크 큰 기능이지만 0단계에서 실현 가능성을 이미 확인했으므로, 여기서는 기능 자체를 완성하는 데 집중한다. 인식 결과가 2단계의 덱(12칸)에 꽂혀야 하므로 2단계가 먼저 끝나 있어야 한다.

- ORB 매칭 + 속성색 보조 판정 이식(데스크톱 v1.23.7 로직).
- 검수 화면(자동 확정 아님, 사용자 확인 후 확정).

**완료 기준**: 스크린샷 샘플 몇 장으로 2단계 덱 화면에 캐릭터가 채워지는 것까지 확인.

### 4단계 — 배포 (FR-6, D-4)

배포할 결과물이 있어야 의미가 있는 단계라 마지막에 둔다.

- `download-site/index.html`에 모바일 섹션 추가, `latest.json`에 `mobile.version`/`mobile.apkUrl`/`mobile.apkSha256` 추가.
- 앱 내 갱신 확인 배너 + 원탭 설치 플로우(`REQUEST_INSTALL_PACKAGES`).

**완료 기준**: 사이트에서 APK를 받아 설치 → 앱 내에서 새 버전이 있다고 감지 → 원탭으로 갱신되는 것까지 실기기 확인.
